Filtering narrows a collection to the rows a client cares about; sorting decides their order. Both are query parameters on the collection, and a little convention keeps them readable.

## Filtering

The simplest, most discoverable form is one query parameter per field:

```http
GET /articles?status=published&author=42
```

For ranges and operators, a common convention is a bracketed or suffixed operator:

```http
GET /articles?createdAt[gte]=2026-01-01&views[gt]=1000
```

Keep the operator vocabulary small and documented (`gte`, `lte`, `gt`, `lt`, `ne`, `in`). Whatever you pick, apply it the same way on every collection.

## Sorting

Accept a `sort` parameter listing fields, with a leading `-` for descending:

```http
GET /articles?sort=-createdAt,title
```

That reads as "newest first, then by title ascending". Define which fields are sortable (sorting on an unindexed column can be expensive) and reject the rest with `400`.

## Applying both in code

export const queryCode = `const articles = [
  { id: 1, status: 'published', views: 1200, title: 'B' },
  { id: 2, status: 'draft', views: 50, title: 'A' },
  { id: 3, status: 'published', views: 300, title: 'C' },
];

function query(items, { status, sort }) {
  let out = items;
  if (status) out = out.filter((a) => a.status === status);
  if (sort) {
    const desc = sort.startsWith('-');
    const key = desc ? sort.slice(1) : sort;
    out = [...out].sort((a, b) => (a[key] > b[key] ? 1 : -1) * (desc ? -1 : 1));
  }
  return out;
}

console.log(query(articles, { status: 'published', sort: '-views' }));`;

| Advantages (Filtering & Sorting) | Trade-offs |
|---|---|
| Client fetches only what it needs — smaller payload | Many query parameters make URLs long and hard to read |
| Server-side filtering beats filtering all the data client-side | Complex filters need a query language (OData, custom) |
| Server-side sort uses a database index — faster than sorting in memory | Filter/sort parameters must be validated to prevent SQL injection |
| Filter and sort combine in a single request | Multi-field sort makes the URL more complex |

## Common mistakes

**Not validating filter parameters**
Symptom:
- `GET /users?sort=; DROP TABLE users--`
- SQL injected through the sort parameter
- Allowlist the fields that can be filtered/sorted: `if (!['name','email','createdAt'].includes(sort)) throw`

**Expensive filters with no index**
Symptom:
- `GET /orders?status=pending` — runs `WHERE status = 'pending'` on a table with millions of rows
- No index on the `status` column — a full table scan on every request
- Add an index on frequently filtered fields, or restrict which filters are supported

> 💡 Real-world examples
>
> **GitHub API:**
> - `GET /repos/\{owner\}/\{repo\}/issues?state=open&labels=bug&sort=created&direction=desc`
> - Multi-dimensional filter and sort in a single request
>
> **Stripe API:**
> - `GET /charges?created[gte]=1609459200&created[lte]=1640995199&limit=100`
> - Range filter via bracket notation — filters between two dates
>
> Sources: [GitHub REST API — issues](https://docs.github.com/en/rest/issues/issues), [Stripe API — pagination and filtering](https://docs.stripe.com/api/pagination)

<Callout title="Allowlist what you filter and sort on">
Never feed raw query params straight into a database query — that invites injection and lets clients sort on slow, unindexed columns. Validate each filter/sort field against an explicit allowlist, and return `400` for anything unrecognized. Flexibility for clients, control for you.
</Callout>
